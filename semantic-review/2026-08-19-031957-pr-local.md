# Parent Orders snapshot restores generation-one ownership bootstrap

The scoped callback removes the circular `hasCurrentOwnerAuthority` predicate from the parent `Orders` listener. A generation-one bridge begins with `ownershipVerified == NO`, so the prior predicate rejected the only callback capable of comparing the snapshot owner with the authenticated UID and establishing authority. The new path remains active/generation admission, document/Auth ownership validation, parsing, then authority assignment before authorized presentation state. It fixes the parent bootstrap deadlock, but it activates a **likely** race in already-registered downstream listeners: their first callback can arrive before parent authority and be discarded without a reliable replay.

**Watch for:** **likely** a cached or independently scheduled support, timeline, or fulfillment snapshot can be lost before the parent callback sets `ownershipVerified`; stage or replay those listeners after parent authority is established.

**Verdict**: NEEDS_CHANGES

## High-level view

The parent snapshot now establishes authority instead of assuming it. It still rejects stopped bridges and stale generations, then refuses to parse or expose the order until the snapshot `userId`/`uid` matches `FIRAuth.currentUser.uid`.

Presentation and mutating entry points remain fail-closed through `hasCurrentOwnerAuthority`, and the auth-state observer still revokes the session by advancing the generation, removing listeners, clearing verified ownership, and emitting denial. The scoped diff adds no parent- or fulfillment-document write.

**Likely**, independent support, timeline, and fulfillment delivery can beat the parent callback. Their callbacks retain the ownership gate, but parent success does not reliably cause each source to publish its dropped initial result again.

<summary>Details</summary>

### Parent snapshot now establishes, rather than assumes, ownership

Before this change, generation one entered `installListenersForGeneration:` with `ownershipVerified` cleared. Its parent callback then called `hasCurrentOwnerAuthority`, which itself requires that flag and the verified owner UID, so no successful parent snapshot could cross the gate. Removing only that precondition breaks the cycle without removing active-session or stale-generation rejection.

The callback validates snapshot ownership against the current Firebase Auth UID before it creates the updated order, sets `ownershipVerified`, records `verifiedOwnerUID`, or emits an authorized state. `presentationState` independently applies `hasCurrentOwnerAuthority`, so a missing or changed Auth user, or a mismatched owner, cannot reveal order, support, timeline, fulfillment, or action data.

### **Likely** lost initial support, timeline, and fulfillment state

The parent, support, timeline, and initial fulfillment listeners are registered in one generation but are independent Firestore subscriptions. Support and timeline return before mutating state until `hasCurrentOwnerAuthority` is true; they retain no pending value. There is no ordering or hand-off in this code that guarantees parent authority is established before a cached or locally scheduled downstream callback runs.

Parent success invokes `restartFulfillmentListenersForGeneration:`, but that method retains registrations with unchanged fulfillment IDs rather than recreating or replaying them. Support and timeline have no restart at all. `includeMetadataChanges:YES` may mask the condition with a later online callback, but it does not guarantee replay for an initial cached/offline result; the **likely** outcome is empty, loading, or timeout-error downstream state despite an authorized parent order. On refresh or bridge reuse, the preexisting support/timeline arrays also remain populated until a new callback replaces them, so an authorized parent emission can **likely** show prior-generation entries briefly.

Stage downstream subscriptions after parent verification, or retain their first values until verification completes and then apply them. Clear downstream arrays at generation start so rebootstrap cannot surface prior-generation data. This preserves the current downstream ownership gate; it is a consistency gap, not a permission bypass.

### Session revocation and collection write posture remain fail-closed

The changed parent callback still exits for stopped bridges and stale generations. Once authority exists, the auth-state listener increments the generation, removes listeners, clears ownership and dependent state, and emits denial; if Auth changes before initial verification, the parent comparison rejects the snapshot instead. The scoped path registers `Orders` and `FulfillmentOrders` snapshot listeners and mutates only in-memory state; it introduces no `setData`, `updateData`, transaction, callable write, or other client write to either collection.
